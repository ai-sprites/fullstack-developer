# 协作与依据

先列出本次真正涉及的仓库与文件，不要求登记业务仓库身份。多人并行时只给会共享的契约、根配置、公共库、CI 和公共测试确定一个编辑者与交接顺序；明确后就可各自处理独立文件，无需先指定总负责人。

共用产品资料时，沿用用户指定或项目明确约定的 host repo、版本和功能或文件集合。实际跨 Git 任务按 Skill 入口复用或补齐 bridge，本地文件可直接读取。前后端共享一份版本记录能说明仓库内容相同，不能证明语义一致或已经获批；确认依据必须来自真实文档或用户说明。

对相同功能的需求、设计与接口检查实际相关的矛盾，保留“待确定”原意与来源。功能索引缺少某类材料不等于整个功能不能做；只暂停需要该内容才能确定的部分。

上游发生变化时先显式比较，说明行为、契约和当前实现受哪些影响，再由当前任务明确是否采用；比较不能暗改已有依据。外部系统链接不等同于随 Git 固定的正文，另行读取时分别注明出处、读取情况和版本依据。

需要反馈时用普通文字写出：功能、依据版本、涉及路径、冲突或缺项、影响及需要补充的信息。只在交接需要时保存到消费项目，依正常团队协作返回上游；不得为让实现继续擅改已确认需求。

跨步骤计划可以是短顺序和一张实际文件表，任务清单只在它确实能帮助分工和验收时采用。完成后以代码差异、实际检查与未完成项更新协作结论，不维护第二份长期状态平台。
