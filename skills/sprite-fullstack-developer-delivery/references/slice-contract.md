# 功能与契约

已确认的接口资源、HTTP 状态、响应结构和分页规则是两端共同约束；保留已有架构规范，不自行把它们降成建议或换用另一套风格。若权威契约为 OpenAPI YAML，行为变化同步主源及相关调用方/提供方并一起验证，不以类型编译通过替代实际契约核验。

沿真实用户路径定位输入、客户端状态、请求、服务规则、持久化与可见反馈。一次完整功能不等于两端都要改；现有接口已支持时可以只改界面，纯服务变化也不必补出新页面。

找出业务规则的权威位置和数据归属。客户端校验改善反馈，服务端在可信边界执行必要验证与授权；不要在两端维护会漂移的独立规则。输入缺失、空值、单位、枚举、错误及异步状态要表达相同含义。

保留当前契约格式和主源，更新真实调用方与提供方涉及的内容。样例仅说明已知行为；不知道后端能力时不能发明字段或用 mock 的成功结果冒充联调。

客户端按实际功能处理加载、空结果、重复操作和错误恢复，服务端处理相应权限、并发和副作用。比如用户提交后超时，两端需要共同说明如何判断结果及安全重试，而不是客户端显示错误、服务端已经执行却无人检查。

对跨端变化检查旧客户端配新服务、新客户端配旧服务，以及缓存和后台任务。兼容增加、消费者切换和旧能力移除应有实际顺序；发布不能原子完成时需说明可共存窗口，不把同一提交当成同步上线。

相关的数据变更结合当前授权和存储能力，核对部分失败、恢复和验证安排。没有数据改变时不引入迁移；已有依赖与模块足够时不再增加框架或跨端公共层。
